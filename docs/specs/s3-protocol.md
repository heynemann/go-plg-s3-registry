# Registry S3 handoff — v1 technical specification

The [control plane](control-plane.md) writes authority; the [data plane](data-plane.md) reads and enforces it. **S3 is the handoff, not a plugin invocation API.** The trust bootstrap is deployment configuration: expected environment, AWS account and bucket/region, active authority epoch, scoped verification keys and maximum proof lifetime. A published record cannot change the rules under which it is trusted.

## Records and identity

Use a versioned namespace and stable, validated IDs as key segments. Use exact-key GET for authority, not prefix listing, timestamp sorting, tags, CDN caching or a replica. Scope all authoritative records and signatures to their declared registry, environment when applicable, and object kind. Verify schema and bounds before allocating for untrusted content. Unknown record versions and invalid or contradictory records are never promoted to serving state.

| Record | Identity and minimum contents | Lifetime / writer |
| --- | --- | --- |
| Plugin registration and trust revisions | Registry/plugin ID; verified owner, on-call and runbook; repository/workflow identity policy; referenced policy revision | Registry administration; immutable revisions, current trust separately resolved at publication |
| Artifact | SHA-256 of the exact distributed archive bytes plus declared length | Create-only by digest. Target environment stores the identical verified bytes before activation; object version IDs are opaque storage references, not artifact identity. |
| Release and admission evidence | Plugin/version → artifact digest and length; source, contract, requested capabilities, test/package evidence, CI identity; verified policy revision and admission proof | Create-only. Retain the trusted binding across routine publisher rotation. Verify both publisher evidence and its authorization for this plugin. |
| Plan and approval | Exact plan digest; plugin/environment; candidate, baseline, expression/schema/bucketing version, seed, ladder, checks, stop conditions and explicit scope of any default switch; approver and independent identity evidence | Immutable; each approval binds one precise plan |
| Decision | Epoch and per-plugin generation, exact predecessor ID, command ID, whole effective rollout state and quarantine set, plan/approval refs, actor, execution identity, reason, evidence and timestamp | Immutable signed object. A losing proposal is never applied just because it is signed. The deny set is environment-wide for this plugin and covers every retained digest. |
| Head | Authority epoch, generation, decision digest | Mutable only by conditional write of a new authorized generation. No deletion or rewind during normal operation. |
| Freshness proof | Exact head identity, epoch, plugin/environment, effective quarantine binding, observation time, expiry | Separate renewal key per head; signed by the narrow freshness role, not by the artifact publisher. Never authoritative for plan changes. |

Use a type-separated signed envelope (DSSE format) for attestations, decisions and proofs. Sign the exact stored payload bytes; the signature must bind the payload type. Hash the exact stored plan bytes and bind that digest to approval; parsing and reserializing a document does not recreate its identity. Use UTC timestamps; reject duplicate fields and invalid scope/type bindings. Pin supported algorithms and verification keys by purpose in trust configuration, not from envelope-supplied key material. Signing-provider integration and machine-readable schemas are implementation deliverables before declaring wire compatibility. S3 encryption and ETags do not replace signature or digest verification.

### Publication format

The namespace is `v1/<registry>`. A plugin's admin-created `plugins/<plugin>/index.json` binds the current registration digest and admitted versions. Each version entry points to an immutable release envelope digest, artifact digest, registration digest, and publisher-key digest. Registration snapshots are under `plugins/<plugin>/registrations/<sha256:digest>.json`; signed releases under `plugins/<plugin>/releases/<sha256:digest>.json`; exact bytes under `artifacts/<sha256:digest>.plg`. The release payload declares its registry and plugin scope, the registration digest, exact archive digest and length, author and workflow attribution, contract, requested capabilities, and the digest and count of the embedded validation report.

Release envelopes use DSSE payload type `application/vnd.go-plg-s3-registry.release.v1+json` and one ASN.1 ECDSA P-256 signature over the SHA-256 of the DSSE pre-authentication encoding. The key ID selects the registered exact KMS key ARN (or a loopback-only fixture key); verifiers use the public key in the trusted registration. The v1 producer emits a single JSON encoding for these records. Verify the stored payload bytes and key, not a normalized representation or the human version. Trust rotation and production activation are separate lifecycle operations; publishing never writes a head.

Publication and publisher administration share the per-plugin index CAS. A publication verified against a superseded binding cannot commit without re-reading and passing the current binding; historical admission still verifies against the immutable registration in its entry. A destination promoter copies the verified records and commits the exact version/digest without installing the source publisher as a writer. Authority and digest inspection never use prefix listing. For missing exact-key reads, grant the necessary bucket-level permission so AWS can return `NoSuchKey` rather than an indistinguishable `403`.

## Conditional publication and audit

1. Upload artifacts, release bindings, plan/approval records and signed decisions with `If-None-Match: *`. On an already-present result, return idempotent success only after verifying the existing binding is identical. Reject conflicting contents. Disable ordinary removal of protected keys: a delete marker can make a previously used key look absent to a conditional create.
2. The protected executor reads the authoritative head and checks expected revision and exact approval. Write the signed next decision, then create an initial head with `If-None-Match: *` or replace an existing head with `If-Match` using its exact ETag. The head write is the commit point. Include generation and decision identity so a rollback authorization does not recreate a prior head body. Enforce conditional headers and writer separation with bucket/IAM policy; use versioning and retain the applied chain. See [AWS conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html) and [bucket policy enforcement](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html).
3. Success means that decision is on the applied chain, not that a host loaded it. `412` means an unmet precondition; reconcile `409`, timeouts, lost responses and unexpected missing heads by reading authority and looking for the command ID. Do not auto-rebase. Walk from the committed head (or a verified historical head) through predecessors to reconstruct applied decisions; loose proposals and freshness renewals are not rollout revisions. Cloud audit logs independently corroborate writes.

One head serializes operations for one plugin/environment, including quarantine. There is no cross-plugin CAS or atomic fleet cutover.

## Freshness and recovery

- **Issuer:** sample the trusted clock before reading the current authoritative head. Verify its committed decision and recovery authorization, bind the proof to that exact head and deny state, and cap expiry from the observation timestamp. Publish independently of the head under a head-specific key. Do not renew from a cached plan, object listing, replica, or merely because the previous proof is valid. If authority changes during issuance, the proof remains bound to the old head and cannot extend the new head; sample time before the read so the old proof cannot acquire a later starting window from a delayed write. The renewal identity can read committed state, sign proofs and write only proof keys; it has no head, plan or deny write authority.
- **Host:** read authoritative head, verify its signed decision, fetch its proof, and confirm the same head is still current before extending freshness. Enforce bounded clock skew, claim scope, head/proof identity, expiry and monotonic observation; use a conservative monotonic local deadline so a wall-clock adjustment cannot extend an accepted proof. A timeout or replay does not reset the clock. Keep the highest verified epoch/revision and matching identity as a replay floor; a restored host with no local floor must bootstrap from the configured authority, never from its artifact cache. A newer committed deny or rollback can narrow admission before a matching renewal or a successful warm-up. Only independently fresh, still-authorized older routes can continue while lagging.
- **Bound:** a host that cannot observe a quarantine may continue starting work only up to an already applicable proof deadline, including the declared skew allowance. No instant fleet revocation or automatic repin. Expiry stops new assignments and new pinned invocations; already-admitted work may finish. Test observed and disconnected hosts separately.
- **Recovery:** do not renew from backup or restore over an active head. Reconcile committed history, artifact bindings and denies under recovery authority; publish a new signed generation before re-enabling renewal. If authority has been lost or moved, fence the old writer/renewal identity and advance the epoch through separately trusted bootstrap configuration; do not let old leases be renewed against the restored namespace. Retain evidence for the last applied generation and quarantine state outside the failed backup's trust boundary. If they cannot be established, remain unavailable. A brand-new host cannot prove an old bucket is stale from that bucket alone.

## Verification

| Layer | What it must prove |
| --- | --- |
| Protocol and selector | Deterministic signature and scope checks, stable bucket vectors and preview parity, malformed and oversized inputs, concurrent state transitions, retry idempotency by command ID, expiry/replay boundaries and authorization while warm-up is in progress. Drive public commands or host-facing operations; inject time and coordination rather than use sleeps. |
| Registry lifecycle against Floci | Use Testcontainers and a digest-pinned [Floci 2.5.0](https://github.com/floci-io/floci/releases/tag/2.5.0) image (`floci/floci@sha256:a0fbf944d7f338cc0856f1ef83831ea749ff2be71956eb7a7fce08fc21458e19`). Isolate the endpoint, credentials and buckets; wait for readiness; clean up containers. Run the public CLI, protected command workflow and at least two real go-plg hosts with distinct packed digests. Assert actual calls, adoption and telemetry through warm-up, ramp, pinned retry, rollback, quarantine, expiry and recovery. Exercise a stale revision and a competing conditional write. No core test hooks. |
| AWS conformance | Run separately on isolated AWS resources. Verify actual cross-account IAM, KMS/access boundaries, versioning/retention, conditional writes and visibility, and recovery against AWS. Test that each principal can do only its job. Passing Floci does not certify AWS IAM, KMS, durability or replication. |

The pinned Floci image passed a local prerequisite probe: create-only duplicate returned `412`, two concurrent writes to one ETag yielded one `200` and one `412`, GET returned the winner, and the previous version remained readable and listed. This was a storage probe, not a registry or AWS conformance run. Keep those checks as a fixture capability test; fail on unsupported behavior rather than weakening the lifecycle assertions. Floci's [S3 documentation](https://floci.io/floci/services/s3/) and its [conditional-write fix](https://github.com/floci-io/floci/pull/566) are reference material.
