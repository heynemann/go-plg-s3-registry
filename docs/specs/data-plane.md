# Registry data plane — v1 technical specification

Source: [lifecycle spec #1](https://github.com/heynemann/go-plg-s3-registry/issues/1). See the [control plane](control-plane.md) and the [S3 handoff protocol](s3-protocol.md).

## API boundary

The **data plane selects and invokes an authorized digest** inside each host process. Hosts read their environment's S3 state and artifacts with a read-only identity. The public integration is a Go SDK with a resolver and a [`go-plg.Storage` implementation](https://github.com/heynemann/go-plg/blob/eed62cd/storage.go#L46-L126), not a registry HTTP API. The registry imports go-plg; go-plg does not import the registry or know about environments, approvals, targeting, S3 or receipts. A guest never receives registry credentials.

| Host-facing operation | Contract |
| --- | --- |
| Configure and start | Host declares authorized registry/environment, trust roots, plugin-to-contract registrations, permissions and resource ceilings, fresh-state limits, retry horizon, and unavailable behavior. Bootstrap is not ready until it has verified authority and the required digest is serving. |
| Sync and report | A background reconciler reads S3, verifies and warms revisions, and reports desired, observed and serving state separately. The host owns process lifecycle and cancellation. No request waits for a sync in the warm path. |
| Select | Given plugin ID, opaque stable application key, and typed allowlisted attributes, return a receipt for exactly one digest or the declared unavailable outcome. No S3, approval system or telemetry query on the warm path. |
| Invoke | Accept the selection receipt, recheck local freshness and quarantine at admission, and dispatch to the typed go-plg key for the exact digest. Reuse this operation on retry; never reselect. Cold historical admission may fetch and verify bytes within its own bounded context and capacity, then recheck admission. |
| Inspect | Local status reports observed authority, effective route, warm-up error, expiration and pool pressure. Host/instrumentation integration may expose these via existing diagnostics; no new listener is required. |

The resolver does not return a long-lived raw plugin handle as an authorization token. The trusted host must use the checked dispatch path for every registry-managed invocation. `Select` alone grants no invocation permission; an expired proof or quarantine observed after selection still blocks `Invoke`. Define invocation start at the local admission check immediately before typed dispatch, ordered against the current deny/freshness snapshot. Calls already admitted, including ones waiting inside go-plg for pool capacity, may finish under their bounded call contexts. This is not a promise to preempt running guests or undo their effects.

## Artifact loading and activation

1. Observe the authenticated current head by exact key. Verify its committed decision, the scope and history ordering, and the referenced deny state. Apply a verified quarantine or explicit rollback restriction before attempting candidate warm-up, even if the new plan isn't ready to serve.
2. Verify signed release admission evidence and SHA-256 of the exact bounded `.plg` archive before opening it with [`plg.OpenArtifact`](https://github.com/heynemann/go-plg/blob/eed62cd/artifact.go#L18-L122). Reject manifest/contract contradictions and requests above the host policy. Registry digest and ownership are not derived from a guest's manifest, an S3 ETag or go-plg's internal provenance digest. Return the verified artifact filesystem to go-plg.
3. Deterministically map the logical plugin ID and full digest to a distinct immutable, slash-safe descriptor key under the host contract registration. `Storage.List` exposes a coherent local snapshot of admitted descriptors, not a listing of all S3 releases. `Storage.Open` binds the exact descriptor to verified bytes; it never resolves a mutable version alias. Stage the current serving keys plus the candidate, not the candidate in place of the baseline.
4. Reconcile with existing go-plg APIs and check the required individual keys with typed lookup and runtime inspection. A reload may apply unrelated removals and additions despite a failure; a successful listing or a candidate precheck is not proof of a warmed serving pool. Reserve capacity for every loaded digest using configured pool maxima and effective memory limits, including draining instances; bound artifact cache bytes and concurrent downloads separately.
5. Atomically publish a local serving snapshot only when the required keys are ready within budget, the revision is still authorized, and its proof is fresh. Discard stale warm-up results. On failure report lag and retain the previous plan only while its proof is fresh and the newly observed state permits its route. Known rollback, quarantine and privilege restrictions take precedence. If no ready route is allowed, use the host-declared unavailable behavior.
6. Remove a key only when there is no protected dispatch reference and it is not needed by the effective route or pending warm-up. Admission, eviction and in-flight lifetime must not race into a wrong-digest call. Historical availability comes from the retention and cold-admission contract, not permanently warm pools. Use atomics or `xsync/v4` for shared state; no mutexes. Keep compilation, signature verification and network I/O off the warm invocation path.

## Selection and receipt semantics

- **Targeting:** v1 is a bounded predicate language over declared `bool`, `string`, and `int` fields (flat keys may include dots). It supports `!`, short-circuit `&&` and `||`, parentheses, typed `==` and `!=`, and `<`, `<=`, `>`, `>=` for integers. String values in expressions use Go double-quoted literals. Referenced fields are validated before evaluation, including under negation. There is no wall-clock, fetch, or configurable function. The registry owns this small grammar and uses one evaluator for CLI preview and host assignment; bucketing is separate. It does not depend on a general-purpose rule engine.
- **Bucketing v1:** use integer basis points from 0 to 10,000. Hash five fields in order with SHA-256: ASCII `go-plg-s3-registry/bucket/v1`, canonical environment ID, canonical plugin ID, the 32-byte rollout seed, and the opaque subject key as supplied by the trusted host. Each field is prefixed by its four-byte unsigned big-endian byte length. IDs are UTF-8 bytes from the signed plan; the seed is decoded from exactly 64 lowercase hex characters. No normalization or case folding is performed on the subject key. Interpret the first eight digest bytes as unsigned big-endian `u`; bucket is `floor(u × 10,000 / 2^64)`, computed with the high word of the multiplication. A matching subject goes to the candidate iff its bucket is strictly less than the rung. The seed, audience and subject identity stay fixed within a ramp. 5% is a fraction of matching keys, not necessarily 5% of observed invocations.
- **Invalid inputs:** absence, type error, invalid routing key or evaluation failure is visible separately from non-match; it cannot select the candidate. Use an authorized, ready baseline for new assignments if permitted; otherwise return unavailable. A first release is full exposure on each ready host, not this candidate-selection path.
- **Selection receipt:** serialize a version, authority/environment and plugin ID, full artifact digest, selection generation/decision, selection timestamp and lane. Do not include the subject key or attributes. The host persists the receipt before its first side effect, associates it with the durable operation, and treats it as trusted workflow data. A receipt identifies a digest, not authority to run it or proof a side effect occurred. The receiver checks scope and prior authorized admission for historical pins; a caller-supplied digest must not make an arbitrary published artifact callable.
- **Retry:** check the declared retry horizon, then current freshness and quarantine at invocation admission. Use the exact receipt digest even after rollback or a default change. Return distinguishable stale-authority, quarantined, expired-receipt, unauthorized and unavailable outcomes. Never substitute another digest. Keep callable artifacts and admission evidence through the maximum configured retry horizon plus margin from last possible assignment; measure that boundary separately from archive retention. The host owns durable operation storage, business idempotency and pins for every plugin in a multi-plugin operation.

## Observability

Distinguish desired generation, observed verified authority, effective route generation, loaded digests and actual invocation lane. Operator views report fresh host coverage, local plan lag, warm-up failures, pool saturation, call outcomes/timeouts and latency. Count targeting errors independently of ordinary non-matches. Report first admissions/exposure separately from pinned retries so retry amplification does not look like assignment growth. Correlate host correctness signals via bounded lane/outcome metadata.

Keep exact digest, decision ID and diagnostic host identity in structured events or traces. Bound metric label values by configuration: lane, decision outcome, operation class and an explicitly bounded set of registered plugin identities if used. Adapt or drop go-plg digest-key labels on exported metrics instead of letting each historical digest create a new series. Never export subject keys, raw attributes, receipts or secrets. Hosts own exporters; missing health data is unknown. See [protocol verification](s3-protocol.md#verification) for the public test seam.

See [the reference dashboard, routing, and alert rules](../observability/dashboard.md). The SDK does not install an exporter or stop/advance traffic based on telemetry.
